TL;DR — the thesis did not hold on this model

GSQ's 2-bit output on Phi-4-mini scores PPL 14.64 against an FP16 baseline of 6.97 — a +110% degradation. llama.cpp's Q2_K costs roughly +41% by comparison.

But this is a real answer, not a broken pipeline. The export is faithful — the dequantized weights correlate 0.88–0.90 with the originals. The number is measuring Genuine GSQ. Which means the method, as configured and applied to a 3.8B dense model, lost.

~0.89 correlation is exactly what a working 2-bit quantization produces. Four discrete levels cannot correlate more strongly with a continuous distribution.

3 · A genuine defect I found in my own output

GSQ emits 2-bit values stored in 4-bit containers. Four distinct codes packed at 4.000 bits/weight. A true 2-bit container would be ~1.9 GB; the file is 3.81 GB.

quantized Linears      64          (32 layers x 2 MLP projections)
logical weights        2,415,919,104
packed int32 elements  301,989,888
EFFECTIVE bits/weight  4.000       <- container
distinct VALUES        4           <- information actually stored

This is a serializer artifact in save_model.py / compressed-tensors, not a GSQ method flaw — but it is what is on disk, and it doubles the footprint for zero quality gain. A second defect: self_attn: false meant attention was never quantized at all, so GSQ's output only reduced precision on the MLP.

The comparison is therefore unflattering in a specific way:

4 · A mistake I made, recorded rather than buried

The first Phase 10 run used a config I built from GSQ's smoke config instead of a production one. The numbers were sitting in the repository the whole time:

                 shipped (real)    first attempt    corrected
num_samples      4096              128              1024
max_length       4096              512              1024
dataset          open_thoughts     c4               open_thoughts
gsq_bits         2                 3 (UNTESTED)     2

That run returned +76% and I did not report it. I flagged it as anomalous, traced the anomaly, and redid it. The corrected run came back worse (+110%), which is internally consistent — 2-bit is more aggressive, and this is a genuine 2-bit quantization.

Lesson (L-022): a thirty-second comparison against a shipped config would have prevented a 19-minute run and a round of reasoning about a meaningless number. When a tool ships example configs, read a real one before writing your own.
5 · Why I think this is the wrong test bed, not a dead method

This is the part I'd want held onto, because it changes what to do next:

  • Calibration was 1/16th of GSQ's recipe. 1024×1024 = 1.05M tokens vs the shipped 4096×4096 = 16.8M. This is a real calibration (16× the smoke run) but not a faithful reproduction. It is the single largest caveat on the result.
  • Phi-4-mini is 3.8B and dense. GSQ's published results are on Llama-3.1-8B/70B, Kimi-K2.5, and Qwen3.5-MoE — 8B to 1T parameters. Small dense models have far less redundancy to absorb aggressive quantization. The method was demonstrated outside this regime, and the negative result may simply reflect that.
  • Cross-ruler caveat. The K-quant figures come from the project's other ruler (llama.cpp binary, different corpus and windowing). Ratios against each ruler's own FP16 are comparable in character; absolute perplexities are not. This project has been burned by a cross-ruler error before (W-002) and it is not being repeated here.
