Which layers and tensors need more bits  ·  Phase 3 complete  ·  2026-09-25

The answer, in one line: the four projections are all equally sensitive, so precision should be spent on layers, not on projection types — and it should be spent at the edges: layer 0 and layer 31 resist quantization roughly twice as hard as the middle of the network.

TL;DR

  • All 128 tensors measured — 32 layers × 4 projections.
  • Projections are flat. Spread across all four is under 1%. Nothing to exploit.
  • Layers are spiked. Layer 0 and 31 are the outliers. That's the signal.
  • Kurtosis predicts it — r = 0.816 at layer level. Cheap and usable.
  • Each extra bit halves the error. Clean, monotone, dependable.
  • A candidate design falls out: 1.81 GB, 76.4% smaller than FP16.
  • One hypothesis refuted, with an honest caveat about the instrument.
  • I caught a bug in my own metric mid-run and had to log it as an error.

One hypothesis refuted — and the caveat that keeps it honest

We were testing whether group scales carry the capacity that plain per-tensor ternary loses. That was the leading explanation for why one ternary attempt collapsed and another ran.

SchemeMean errorvs per-tensor
per-tensor0.5363—
group 1280.51384.2% better
group 320.50705.5% better

Going from one scale per tensor all the way to a scale per 32 weights improves things by 5.5%. That cannot explain the difference between a model that collapsed and one that ran.

But here is the honest part. Ternary error is ≈0.51–0.54 for every scheme, including group-32. Half the weight energy is gone in all cases. A 51% weight error cannot map linearly to capability, because BitNet-class models work in exactly that regime — they're trained into it.

So the refutation is real as measured on weight-space error, and this metric is simply the wrong instrument for judging ternary. The question stays open, and it cannot be settled here. That caveat is written into the receipt, not glossed over.

My own error — logged as W-006

I chose weight-space reconstruction error as the sensitivity instrument without first checking it could measure the thing being asked. It's the standard cheap approach, and it's the right tool for comparing uniform bit budgets. For ternary it's meaningless.

What caught it: the ternary error was suspiciously identical across every group size. A metric that returns the same answer no matter what you change is not measuring what you changed.

The bug underneath: my first run reported 2-bit scoring worse than ternary — impossible, since 2-bit has more levels. My quantizer's scale let reconstructed values overshoot the group maximum, so it added error instead of removing it.

broken:  step = 2 * scale / (nlev - 1)   with clipping past +/- scale
fixed:   step = scale / (2^(bits-1) - 1)  symmetric, no overshoot

The fix has a built-in check: at 2 bits it must reproduce absmax ternary exactly, and it now does. The bad run was killed before writing output, so no invalid artifact exists.

Cost: one wasted run. Caught by noticing an impossible ordering, not by luck.
