# AIK-07B — Kanban MVP acceptance matrix

**Status:** design acceptance cases, not executed tests. D-1–D-5 are owner-decided in the [receipt](../receipts/AIK-07B-OWNER-DECISIONS.md) and integrated in the [contract](../deliverables/KANBAN-MVP.md). A pass requires the stated observable result; a fail is any contrary result. Fixtures use two boards, two verified actors with different grants, a distinct authorized removal approver, and a durable restart point. Implementation remains blocked pending three audit/refinement rounds, final owner approval, and evidence-backed technical selection.

| ID | Guarantee / scenario | Pass criterion | Fail criterion |
|---|---|---|---|
| A-01 | Stable identity: a human and agent each authenticate; submit a different actor name in the request. Repeat with only a shared service key. | Attribution uses the verified actor ID; forged name is ignored/rejected; shared key alone cannot impersonate either actor. | Supplied name or key determines end-actor attribution. |
| A-02 | Board-scoped reads: actor with board A read grant requests A and B task, history, snapshot, and replay. | A succeeds; all B paths deny without disclosing B content or cursor data. | Any B data leaks. |
| A-03 | Board-scoped writes: actor has A write grant only; attempt create, edit, complete, reopen, removal request, and approval on B; attempt approval on A without approve grant. | Every unauthorized operation denies; task, revision, audit, and feed remain unchanged. | Any unauthorized state change or event appears. |
| A-04 | Attribution: authorized human creates/edits and agent completes a task. | Each mutation and event points to the same verified actor, board, task, operation, time, and prior/new revision; history is append-only. | Missing, forged, mutable, or mismatched attribution. |
| A-05 | Schema/lifecycle: create with all required fields, then with a missing required field; edit, complete, reopen; attempt stale edit and complete after removal. | Valid task has stable ID, required fields, service timestamps and revision; invalid input rejects; transitions follow spec; stale edit conflicts; removed task rejects writes. | Invalid schema accepted, invalid transition, silent overwrite, or incorrect timestamp/revision. |
| A-06 | Same write retried with identical key/payload after response loss and restart; then same key with changed payload. | Retry returns original outcome/IDs with one mutation, audit record, and event; changed payload fails. | Duplicate effect or changed payload accepted. |
| A-07 | Repeat complete/reopen in destination state; retry a denied or stale request after grants/revision change. | No duplicate mutation/event; previous rejected request cannot turn into an accepted write merely by retry. | Repeated or formerly rejected request adds an unrequested change. |
| A-08 | Request removal, deny it, request again, then have an eligible approver approve the pending request at the reviewed revision; try direct removal and approval without pending request. | Requests/decisions carry actor/time/reason/revision; denial preserves task; only valid approval creates tombstone; bypass attempts deny. Self-approval always denies, even if the requester has an approve-removal grant; approval records a reason and the current task revision. | Removal without valid pending decision, lost history, or policy violation. |
| A-09 | Snapshot at cursor C; commit several changes while client is disconnected; replay after C. | All missed board events arrive in committed order, once in logical state after client deduplication; no gap or cross-board event. | Missing, reordered, or unauthorized event. |
| A-10 | Disconnect during delivery, restart service, reconnect with last acknowledged cursor; retry an ambiguous write. | Committed task/history/idempotency/event survive; replay may redeliver but yields one logical state; uncommitted change is absent. | Lost committed change, duplicate mutation, or cursor gap. |
| A-11 | Present an expired cursor and attempt to infer position from cursor bytes; also verify no automatic expiry in the private bounded trial. | Explicit expired-cursor response requires a fresh consistent snapshot; cursor grants no access and exposes no authoritative semantics. | Silent truncation, unauthorized access, or cursor-derived authority. |
| A-12 | Supply Mind execution record, Relay todo item, Control approval/chat event, or dashboard datum as a task authority or execution command. | None creates/changes a board task or authorizes execution without a separately authenticated, authorized task mutation; board data stays within its granted scope. | Cross-system data implicitly becomes a task write or command. |
| A-13 (D-1) | Inspect deployment design and exercise task reads/writes through Relay and Control clients. | One dedicated logical service/store is authoritative; Echo operates under Eddie's policy authority; clients create no competing task authority. | A client or existing component becomes a second task store or grants policy authority to Echo. |
| A-14 (D-2) | Eddie directs grant/revocation; Echo administers it; test access before and after revocation, including feed replay. | Grant changes follow Eddie's direction and current board grants govern every operation; actor ID comes from verified context, never a shared key. | Echo sets policy independently, revoked access succeeds, or key impersonates an actor. |
| A-15 (D-3) | Requester also holds approve grant and attempts to approve their own pending removal; a different authorized approver tries stale and current revisions. | Self-approval and stale revision deny without mutation; distinct authorized approval at current revision records reason, actor, and revision. | Self-approval, stale approval, or missing decision evidence succeeds. |
| A-16 (D-4) | In a private bounded trial, restart after audit, tombstone, event, and idempotency writes; read removed history as authorized and unauthorized actors. | All four records persist without automatic expiry; only authorized readers see removed history; expired cursor gives explicit fresh-snapshot instruction. | Any trial record expires automatically or is lost on restart, removed history leaks, or cursor silently skips data. |
| A-17 (D-4 gate) | Propose broader/production use before a numeric retention policy is approved. | Broader use stays blocked until evidence-backed numeric periods, capacity/deletion behavior, and Eddie's approval are recorded. | Trial no-expiry rule is silently carried into production or broader use begins without approval. |
| A-18 (D-5) | Fetch snapshot and replay changes; inspect JSON shape, cursor, priority, and optional source reference. | JSON snapshot has opaque cursor; events are durable and ordered; expired cursor forces fresh snapshot; priority accepts only `low|normal|high`; `source_ref` is optional, opaque, and grants no authority. | Format, ordering, expiry, field, or authority rule differs. |

**Coverage:** identity and authorization A-01–A-03/A-14; attribution/audit A-04; fields and lifecycle A-04–A-05; idempotency A-06–A-07; removal A-08/A-15; ordered replay and retention A-09–A-11/A-16–A-18; authority boundaries A-12–A-13; production gate A-17. D-1–D-5 policy is recorded; all rows remain future implementation checks, not claims of passing runtime behavior. Numeric production retention, concrete identity source/lifecycle, database/runtime/hosting/deployment, snapshot handoff mechanics, and event transport require discovery evidence and approval before broader use.
